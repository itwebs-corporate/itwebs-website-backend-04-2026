# ITWEBS API

Backend и встроенная админка: Java 21, Spring Boot, PostgreSQL, S3-совместимое хранилище MinIO и Swagger/OpenAPI. Данные главной страницы из макета хранятся как отдельные редактируемые элементы: текст, ссылка или изображение. Админка доступна по `/admin` и запускается вместе с бэкендом; отдельные Node.js и сборка фронтенда не нужны.

## Структура

```text
src/main/java/ru/itwebs/cms/
├── bootstrap/    # начальные элементы контента по макету
├── config/       # HTTP Basic и OpenAPI
├── controller/   # REST-маршруты и обработка ошибок
├── dto/          # JSON-запросы и ответы
├── entity/       # JPA-сущности
├── repository/   # PostgreSQL
└── service/      # бизнес-логика и работа с S3
```

## Админка на сервере

Админка входит в тот же Docker-образ, что и бэкенд. После переноса обновлённых исходников на сервер выполните из папки проекта:

```bash
docker compose --env-file .env up --build -d
```

Команда использует существующий `.env`, собирает и запускает бэкенд вместе с админкой. Существующие тома БД и файлов сохраняются. Откройте `http://IP-СЕРВЕРА:9999/admin` (тот же адрес и порт, что у бэкенда) и войдите с `ADMIN_EMAIL` / `ADMIN_PASSWORD` из `.env`.

Изменения должны попасть на сервер перед выполнением команды; локальное редактирование не публикует их автоматически.

## Работа с админкой

Вход: `ADMIN_EMAIL` и `ADMIN_PASSWORD` из `.env`. Данные входа хранятся только в памяти вкладки; после перезагрузки страницы нужно войти заново. Кнопка «Выйти» очищает данные из интерфейса. HTML/CSS/JS формы доступны без входа, административные данные и операции защищены HTTP Basic.

Разделы: тексты/ссылки/картинки сайта (поиск и фильтр по разделу), медиатека (загрузка, описание, удаление), заявки (просмотр и статус обработки), статьи (блоки текста, заголовки, списки, цитаты, картинки, обложка, категории, SEO и дата публикации), категории. Удаление требует подтверждения. Ошибки API отображаются в форме, несохранённые изменения при ошибке сохраняются. При конфликте версии закройте форму и снова откройте запись, чтобы загрузить актуальные данные. Поиск статей работает на текущей странице; другие статьи доступны кнопками пагинации.

Для остановки: `docker compose --env-file .env stop`.

## Запуск

Создайте `.env` в корне проекта и задайте `POSTGRES_PASSWORD`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` (от 6 символов) и `S3_SECRET_KEY`. При необходимости задайте `POSTGRES_DB`, `POSTGRES_USER` и `S3_ACCESS_KEY`; для них есть значения по умолчанию. Затем выполните `docker compose --env-file .env up --build -d`.

API слушает `http://localhost:9999`. PostgreSQL слушает `15432` снаружи и внутри контейнера. MinIO API доступен на `127.0.0.1:19000`, консоль — на `127.0.0.1:19001`; внутри сети Docker приложение использует `minio:9000`. Dockerfile собирает приложение без выполнения тестов.

## Swagger и авторизация

Swagger UI: `http://localhost:9999/swagger-ui.html`. OpenAPI JSON: `http://localhost:9999/v3/api-docs`. Каждый REST-контроллер и его маршруты описаны в Swagger. Публичные операции доступны без пароля; для `/api/admin/**` используется HTTP Basic с `ADMIN_EMAIL` и `ADMIN_PASSWORD` из `.env`. В Swagger нажмите **Authorize** и введите эти данные.

## Передача заявок в amoCRM

После OAuth-подключения каждая новая заявка сайта создаёт сделку в воронке `Заявки с сайта` на этапе `Новая заявка` и связанный контакт с телефоном и/или почтой. Текст обращения и предпочтительный способ связи добавляются примечанием к сделке. Заявка в любом случае сначала сохраняется в PostgreSQL. Состояние отправки отображается в `GET /api/admin/leads`; ошибки повторяются автоматически.

Используется внешняя интеграция amoCRM: её OAuth-реквизиты передаются кнопкой подключения на сервер, поэтому вручную задавать `AMOCRM_CLIENT_ID` и `AMOCRM_CLIENT_SECRET` не нужно. Добавьте в `.env` постоянный `AMOCRM_TOKEN_ENCRYPTION_KEY`, сгенерированный командой `openssl rand -base64 32`; не меняйте его после первого успешного подключения, иначе сохранённые токены невозможно будет расшифровать. Для OAuth amoCRM обеспечьте доступность `/api/integrations/amocrm/secrets` и `/api/integrations/amocrm/callback` на настроенном HTTPS-домене `itwebs.ru`. После деплоя откройте `https://itwebs.ru/api/admin/integrations/amocrm/authorize`, войдите с HTTP Basic данными администратора, нажмите кнопку и разрешите доступ аккаунту `itwebs.amocrm.ru`. amoCRM передаст OAuth-реквизиты на `/api/integrations/amocrm/secrets`, затем вернётся на `/api/integrations/amocrm/callback`; backend сохранит их зашифрованными.

Новые заявки, полученные до OAuth-подключения, автоматически не переносятся. Укажите другую воронку или этап через `AMOCRM_PIPELINE_NAME` и `AMOCRM_STATUS_NAME`. Назначение менеджера необязательно и задаётся через `AMOCRM_RESPONSIBLE_USER_ID`.

## Маршруты

| Метод | Путь | Доступ | Назначение |
| --- | --- | --- | --- |
| GET | `/api/content?section=...` | публичный | опубликованный контент |
| GET | `/api/content/{id}` | публичный | один опубликованный элемент |
| GET | `/api/pages/services` | публичный | готовый ответ страницы услуг с общими блоками и связанными кейсами |
| GET | `/api/pages/product` | публичный | страница продукта с демонстрацией ProBuilder и связанными проектами |
| GET | `/api/pages/outstaff` | публичный | страница аутстаффинга со специалистами, фильтрами и общей командой |
| GET | `/api/pages/cases` | публичный | готовый ответ страницы кейсов с фильтрами и вложенными проектами |
| GET | `/api/media/{id}` | публичный | файл изображения |
| POST | `/api/leads` | публичный | сохранить заявку |
| GET, POST | `/api/admin/content` | админ | список всех элементов, создание |
| GET, PUT, DELETE | `/api/admin/content/{id}` | админ | просмотр, изменение, удаление |
| GET, POST | `/api/admin/media` | админ | список файлов, загрузка multipart |
| GET, PUT, DELETE | `/api/admin/media/{id}` | админ | метаданные, alt-текст, удаление |
| GET | `/api/admin/leads` и `/api/admin/leads/{id}` | админ | просмотр заявок |
| PATCH, DELETE | `/api/admin/leads/{id}` | админ | статус и удаление |

Фронтенд страниц услуг и кейсов запрашивает один маршрут на страницу. Ответ содержит `page` и объект `sections`; ключи секций — имена контентных разделов, значения — группы записей с полями по `itemKey`. В карточках кейсов поле `project` уже содержит связанную карточку проекта, а в карточках страницы услуг она доступна в `services-page-project-items`. Категории фильтров кейсов находятся в `cases-page-filters`; у кейса может быть несколько полей `filter1`, `filter2` и т. д. Общие шапка, форма и подвал входят в ответ каждой страницы. Редактирование по-прежнему выполняется через универсальные `/api/admin/content` и `/api/admin/media` маршруты.

В `GET /api/pages/services` секция `services-page-title-words` содержит группы `word-1`, `word-2`, `word-3` с полем `word`: «разработки», «поддержки», «автоматизации». Используйте этот список в порядке ответа для анимации заголовка. В `services-page` также добавлен полный `title` группы `automation`; основной `title` и группа `outstaff` сохранены. Секции `services-page-seo` и `cases-page-seo` содержат поле `eyebrow` без группы со значением «Для поискового интента». Все поля редактируются через CMS. Обновление добавляет только отсутствующие записи один раз при запуске новой версии, с маркером `_system/servicesCasesCopySeedV1`; существующие значения не перезаписываются, удалённые после обновления поля не восстанавливаются при перезапуске.

При первом запуске или обновлении старой базы однократно создаются недостающие элементы контента по десктопному макету: шапка, первый экран, бренды, услуги, проекты, показатели, технологии, аутстаффинг, команда, форма связи, SEO-блок и подвал. Уже изменённые элементы не перезаписываются; после заполнения удалённые администратором элементы не восстанавливаются при перезапуске. Каждый текст, ссылка, значок и фотография представлены отдельным элементом; карточки объединяются через `groupName`. `sortOrder` задаёт порядок. Фоновые градиенты и оформление не являются данными backend.

Отдельные исходные картинки из Figma не предоставлены: загрузите их через `POST /api/admin/media`, затем укажите `mediaId` в нужном элементе типа `IMAGE` через `PUT /api/admin/content/{id}`. Для изображения также можно задать `href` и альтернативный текст (`value`). Публичный API возвращает URL изображения в `mediaUrl`. Админского HTML-интерфейса нет; редактирование доступно через Swagger.

Для продакшена нужны HTTPS, резервные копии PostgreSQL и бакета, а также миграции схемы вместо текущего `ddl-auto: update`.

Настройка автоматического деплоя по GitHub webhook описана в [deploy/README.md](deploy/README.md).

## Страница Outstaff

`GET /api/pages/outstaff` возвращает опубликованные данные страницы. Все её тексты, ссылки, карточки и принадлежность специалистов к фильтрам редактируются через общий CRUD `/api/admin/content`. Создание: POST; чтение списка: GET; чтение, обновление и удаление по ID: GET, PUT, DELETE `/api/admin/content/{id}`. Данные и ID текущих полей видны в ответе страницы. PUT принимает полный ContentRequest, включая sectionName, itemKey, groupName, type, label, value, href, mediaId, sortOrder, published.

Одинаковые подписи в разных местах демонстрации используют одно поле. Даты, цена и контакты в демонстрации — рекламные примеры, а не действующие реквизиты или подписка backend. Вёрстку и отображение данных из API подключает фронтенд.

Форма Outstaff на текущем сайте не содержит поля задачи. Для POST /api/leads фронтенд может сформировать необязательный `message` из выбранного специалиста и грейдов. Product имеет textarea с HTML name=task; в запрос API его текст передаётся как `message`. Канал связи в обеих формах передаётся как `contactMethod`, а не HTML name=channel. Проверка не отправляла реальные заявки.

Описание задачи `message` в POST /api/leads необязательно: поле можно не передавать, передать null, пустую строку или пробелы. Максимум — 5000 символов. Отсутствующее описание сохраняется как пустая строка, совместимая с существующим NOT NULL столбцом базы. В amoCRM блок сообщения добавляется только при наличии текста. Имя, согласие и хотя бы один контакт (телефон или почта) остаются обязательными.

Сверка относится к локальному backend. При проверке 2026-10-12 публичные `/api/pages/outstaff` и `/api/pages/product` на порту 9999 отвечали HTTP 401; наличие созданных полей в серверной базе этим ответом не подтверждено. Публикация изменений и подключение фронтенда к новым данным остаются отдельным шагом.


## Блог: API и подключение фронтенда

### Маршруты

| Назначение | Метод и путь |
|---|---|
| Тексты и общие блоки `/blog` | `GET /api/pages/blog` |
| Общие блоки шаблона статьи | `GET /api/pages/blog-article` |
| Категории фильтров | `GET /api/blog/categories` |
| Карточки статей | `GET /api/blog/articles?page=0&size=20&category=web` |
| Статья | `GET /api/blog/articles/{slug}` |
| Рекомендации | `GET /api/blog/articles/{slug}/related?limit=3` |
| Список/создание статей | `GET/POST /api/admin/blog/articles` |
| Чтение/обновление/удаление статьи | `GET/PUT/DELETE /api/admin/blog/articles/{id}` |
| Список/создание категорий | `GET/POST /api/admin/blog/categories` |
| Чтение/обновление/удаление категории | `GET/PUT/DELETE /api/admin/blog/categories/{id}` |

Все административные операции требуют существующий HTTP Basic с ролью ADMIN. Публичные GET доступны без авторизации. Swagger: `/swagger-ui/index.html`; OpenAPI: `/v3/api-docs`.

### Список и публикация

Ответ списка: `items`, `page`, `size`, `totalElements`, `totalPages`. Нумерация с нуля, размер 1–100, page 0–100000. Для кнопки «Все» параметр category не передаётся; категории без опубликованных статей дают пустой список. Публичный порядок — `publishedAt DESC, id DESC`; административный — `updatedAt DESC, id DESC`. Административный список также принимает `status=DRAFT|PUBLISHED`.

Карточки формируются из статей, отдельного хранения карточек нет. Поле `url` ведёт на `/blog/{slug}`. Карточка содержит обложку, категории, время чтения, название и excerpt; тело возвращается только в ответе конкретной статьи. Запросы списка и рекомендаций выбирают только поля карточек, категории загружаются одним запросом на страницу. Ответ статьи: `article` (карточка), `blocks`, `images`, `seoTitle`, `seoDescription`.

Черновик допускает отсутствие обложки и excerpt, пустые blocks/categoryIds. Публикация требует непустой текст заголовка, slug, описание, обложку, хотя бы один блок и категорию. Статус `PUBLISHED` с датой в будущем обеспечивает отложенную публикацию без фонового задания. Черновики и будущие статьи возвращают 404 в публичном API, включая рекомендации. У первой публикации publishedAt=null устанавливает текущую дату; при обновлении null сохраняет предыдущую дату. Для новой даты передайте явный ISO 8601 timestamp с часовым поясом. `DRAFT` скрывает статью, сохраняя дату для последующей публикации.

Slug: строчные латинские буквы, цифры и одиночные дефисы между частями; уникальность статьи и категории обеспечивается отдельно ограничениями БД. Категория `all` зарезервирована. Изменение slug меняет публичный URL: автоматические редиректы старого адреса не создаются.

### Создание и редактирование статьи

Минимальный черновик:

```json
{
  "title": "Первая статья",
  "slug": "first-article",
  "excerpt": "",
  "blocks": [],
  "status": "DRAFT",
  "categoryIds": []
}
```

Создание возвращает 201 и Location. Для PUT передайте полный ArticleRequest и `version` из `article.version` последнего GET. Категории используют version из своего GET. POST выполняется без version. Устаревшая версия даёт 409: загрузите свежие данные и согласуйте изменения. Защита действует также при одновременных запросах через JPA optimistic locking.

Обложка задаётся `coverMediaId`. Изображения сначала загружаются через существующий `POST /api/admin/media`; используются только существующие ID. `readingMinutes` можно задать явно (1–1000); иначе оно вычисляется по тексту блоков из расчёта 200 слов в минуту, минимум 1. SEO title/description при пустом значении берутся из title/excerpt. Канонический адрес конкретной статьи фронтенд строит из её slug и публичного домена.

### Формат содержимого

Упорядоченный список блоков поддерживает:

```json
[
  {"type":"HEADING","text":"Введение","level":2},
  {"type":"PARAGRAPH","text":"Обычный текст"},
  {"type":"QUOTE","text":"Цитата"},
  {"type":"BULLET_LIST","items":["Первый пункт","Второй пункт"]},
  {"type":"NUMBERED_LIST","items":["Первый шаг","Второй шаг"]},
  {"type":"IMAGE","mediaId":7,"alt":"Описание картинки","caption":"Подпись"}
]
```

HEADING поддерживает уровни 2–4. H1 — название статьи. Текстовые блоки требуют непустой text, списки — непустой items, IMAGE — mediaId. Поля других типов не допускаются. В IMAGE alt и caption необязательны; alt блока переопределяет описание медиазаписи. `images` ответа содержит URL и alt всех использованных изображений, включая обложку. HTML и Markdown в тексте не интерпретируются: фронтенд должен выводить строки как текст, без `innerHTML`/`dangerouslySetInnerHTML`. Якоря заголовков можно создавать из индекса блока, например `block-0`.

Ограничения: до 200 блоков, до 100 пунктов списка, до 20 категорий; до 20 000 символов text, 5 000 символов пункта списка; суммарный сериализованный body до 1 000 000 символов. Статья сохраняется целиком одной транзакцией вместе со связями категорий и изображений.

### Контент страницы

Для всех текстов используется существующий `/api/admin/content`. GET страницы возвращает ID каждого поля; по нему доступны GET/PUT/DELETE. Новые записи создаются POST.

| sectionName | Назначение |
|---|---|
| `blog-page` | eyebrow, title, description, allLabel, defaultTag, readingTimeLabel, emptyLabel, loadMoreLabel, floatingCta |
| `blog-page-title-words` | Группы сменяемых слов заголовка: поле word, порядок sortOrder |
| `blog-page-meta` | title, description, canonical списка блога |
| `blog-page-seo`, `blog-page-seo-items` | Нижний SEO-блок, expandLabel/collapseLabel |
| `blog-article-page` | relatedTitle, servicesTitle, defaultTag, readingTimeLabel, floatingCta |
| `blog-article-page-seo`, `blog-article-page-seo-topics` | Нижний SEO-блок шаблона статьи |
| `blog-article-service-items` | serviceGroup — ссылка на groupName существующей services-page-catalog; порядок sortOrder |

Общие header/contact/footer включаются в ответы страниц. Категории блога — отдельные сущности; кнопка «Все» — текст страницы. Общая метка «Разработка» — defaultTag, остальные метки карточки берутся из её categories. Подпись времени чтения — отдельный текст; число — readingMinutes.

Шаблон статьи также возвращает `services-page-catalog`: сопоставьте serviceGroup с groupName каталога. Отсутствующую или скрытую услугу пропускайте. Услуги редактируются через их существующие записи контента, изменения общие для всех страниц. Рекомендации — последние опубликованные статьи без текущей; запрос может вернуть меньше limit.

### Хранение и ошибки

Добавлены таблицы blog_articles, blog_categories и таблицы связей blog_article_categories/blog_article_images. Схему создаёт существующая настройка Hibernate `ddl-auto: update`; отдельный механизм миграций проект пока не использует. Даты хранятся как Instant (UTC). Внешние ключи защищают связи; slug имеет уникальный индекс. Обложка и изображения содержимого сохраняются в связях с медиазаписями: удаление используемого изображения блокируется, включая использование в черновиках. Привязка изображений и их удаление используют блокировку медиазаписей, чтобы конкурентное удаление не убрало файл во время сохранения статьи.

Начальные тексты и категории Mobile/Web/CRM/E-com/AI добавляются один раз, в транзакции, с маркером `_system/blogPageSeedV1`. Существующие поля сохраняются. SEO-тексты копируются из существующих секций в отдельные секции блога при первом запуске; затем редактируются независимо. Демонстрационные статьи не добавляются. После удаления категорий или текстов они не появляются снова при перезапуске.

Ошибки возвращаются как ProblemDetail: 400 — валидация, 404 — отсутствующая запись/публичная статья, 409 — дубликат slug, устаревшая версия или используемая связь. Категорию с привязками удалить нельзя: сначала измените categoryIds статей. DELETE статьи возвращает 204, удаляет её связи и сохраняет медиафайлы. Для временного скрытия используйте DRAFT.

Фронтенд нужно подключить к этим API вместо демонстрационных данных. Бэкенд не изменяет исходники фронтенда и не разворачивается на сервер автоматически.
