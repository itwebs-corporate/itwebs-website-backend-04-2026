# ITWEBS API

Java 21, Spring Boot, PostgreSQL, MinIO/S3. Встроенная админка: `/admin`. Swagger: `/swagger-ui.html`, OpenAPI: `/v3/api-docs`.

## Модель контента

Страница — отдельная запись `SitePage` с фиксированным каркасом `SiteBlock`. Блок содержит один документ с полями и повторяющимися элементами. Его схема, тип, место на странице и набор полей заданы при переносе контента; редактор меняет содержимое, а не создаёт произвольные блоки. В базе больше не требуется отдельная строка на каждую надпись. `sectionName`, `groupName`, `itemKey`, `filter1` и теги не используются для сборки нового публичного ответа или определения связей.

Переиспользуемый контент хранится отдельно:

| Сущность | Каталог API | Содержимое |
| --- | --- | --- |
| `ServiceOffering` | `services` | Описание, адрес, стоимость, FAQ, стек, процессы, задачи, аудитория, сотрудничество, примеры работ |
| `CaseStudy` | `cases` | Карточка, заголовок детальной страницы, клиент, задача, решение, результат, разделы текста, стек, галерея |
| `OutstaffSpecialist` | `specialists` | Направление, грейд, опыт, доступность, навыки, стоимость, фотография |
| `TeamMember` | `team` | Имя, должность, биография, фотография |
| `BlogArticle` / `BlogCategory` | `/api/blog` | Статьи с типизированными блоками и категориями |

Каталоги используют общую базовую таблицу `catalog_entries` и отдельные таблицы каждого вида сущности через JPA JOINED. У каждого каталога свои категории. Категории, медиа, примеры работ услуги и подборки страниц связаны внешними ключами.

FAQ, технологии, процессы, решаемые задачи, аудитории и модели сотрудничества услуг хранятся в справочнике `service_components` с фиксированными типами `FAQ`, `STACK`, `PROCESS`, `TASK`, `AUDIENCE`, `COOPERATION`. Услуга выбирает элементы через `service_component_links`: внешний ключ, порядок и необязательное индивидуальное переопределение названия, описания или стоимости. Одинаковый общий элемент хранится один раз. Его редактирование меняет все связанные услуги, кроме явно переопределённых полей. Заголовки разделов остаются собственными полями услуги. Логотип технологии связан с медиа внешним ключом.

`PageCollection` определяет подборку на странице: весь каталог либо конкретные записи в выбранном порядке. Можно переопределить заголовок, описание и alt карточки только для этой страницы; у команды также должность, у специалиста — данные `specialist` целиком. Изменение исходной записи отражается во всех подборках, кроме явно переопределённых полей. Повторное использование блока оформляется связью `page_reused_blocks`; например, Product и Services используют общий SEO-контент. `ownerPage` в ответе блока указывает страницу, через которую он редактируется.

## Работа в админке

1. Откройте `/admin`, войдите с `ADMIN_EMAIL` / `ADMIN_PASSWORD`.
2. В разделе «Категории услуг» создайте нужную категорию.
3. В разделе «Услуги» нажмите «Добавить».
4. Заполните название, адрес, описание, категорию и стоимость. Полная ссылка отображается под адресом.
5. Примеры работ выберите из кейсов. Для FAQ, стека, процессов, задач, аудитории и моделей сотрудничества выбирайте элементы из списков. Общие записи сначала создаются в отдельных одноимённых разделах справочников. Выбранные элементы можно убирать из услуги и перемещать; раздел «Индивидуальный текст для этой услуги» позволяет переопределить отдельные поля. Отключение переопределения возвращает общее значение; включённое пустое описание намеренно убирает описание только в этой услуге.
6. Включите «Показывать на сайте» и сохраните. Без этой галочки запись остаётся черновиком.

Для примеров работ сначала создайте кейсы в разделе «Кейсы», затем выберите их в услуге. Черновой кейс виден редактору, но исключается из публичного ответа услуги.

В разделе «Страницы» выберите страницу, затем нужный блок. Общие шапка, форма и подвал помечены как общие и меняются сразу на всех страницах. Отдельная страница «Общие блоки» управляет их публикацией. Подборки редактируются кнопкой «Выбрать записи»: весь каталог или выбранные записи с настройками отображения.

SEO и публикация страницы сохраняются основной кнопкой формы страницы. Содержимое блока и подборки сохраняется в собственной форме. Переход между формами не сохраняет несохранённые изменения автоматически.

Разделы статей, медиатеки и заявок сохранены. Изображение можно загрузить прямо в поле выбора; загрузка выбирает файл, а «Сохранить» привязывает его к записи. Для публикации статьи требуются описание, обложка, категория и содержимое.

Логин хранится только в памяти вкладки. После перезагрузки нужен повторный вход. Если получен конфликт версии, откройте запись заново и согласуйте изменения. Поиск в списках каталогов и статей работает на текущей странице; остальные записи доступны через пагинацию.

## Публичные API

| Метод | Маршрут | Ответ |
| --- | --- | --- |
| GET | `/api/pages` или `/api/pages/home` | Главная |
| GET | `/api/pages/services` | Страница услуг |
| GET | `/api/pages/cases` | Страница проектов |
| GET | `/api/pages/outstaff` | Страница аутстаффинга |
| GET | `/api/pages/product` | Продукт |
| GET | `/api/pages/blog` | Контент страницы блога |
| GET | `/api/pages/contacts` | Контакты, отделы, офис, реквизиты |
| GET | `/api/pages/policy` | Разделы политики |
| GET | `/api/pages/services/{slug}` | Шаблон и конкретная услуга |
| GET | `/api/pages/cases/{slug}` | Шаблон и конкретный кейс |
| GET | `/api/pages/outstaff/{slug}` | Шаблон и конкретный специалист |
| GET | `/api/pages/team/{slug}` | Шаблон и конкретный участник команды |
| GET | `/api/pages/blog/{slug}` | Статья, общие блоки, рекомендации |
| GET | `/api/catalog/{kind}` | Карточки каталога с пагинацией |
| GET | `/api/catalog/{kind}/categories` | Категории каталога |
| GET | `/api/catalog/{kind}/{slug}` | Полная запись без общего шаблона страницы |
| GET | `/api/blog/articles` | Карточки статей с пагинацией |
| GET | `/api/blog/articles/{slug}` | Статья |
| GET | `/api/blog/articles/{slug}/related` | Рекомендации, `limit=1..12` |
| GET | `/api/blog/categories` | Категории статей |
| GET | `/api/media/{id}` | Изображение |
| POST | `/api/leads` | Сохранить заявку |

`kind`: `services`, `cases`, `specialists`, `team`. Примеры фильтрации: `/api/catalog/services?category=mobile`, `/api/catalog/specialists?category=web`. Категория задаётся её slug. Неизвестная категория даёт пустой список. `page=0..100000`, `size=1..100`; по умолчанию 0 и 20. Сортировка каталогов: `sortOrder`, затем `id`. Ответ: `items`, `page`, `size`, `totalElements`, `totalPages`. Только опубликованные записи; скрытая детальная запись даёт 404.

Ответ обычной страницы содержит:

- `page`, `path`, `title`, `seoTitle`, `seoDescription`, `canonical`;
- `blocks`: фиксированные блоки с `key`, `type`, `shared`, `schema`, `data`;
- `collections`: подборки карточек, индексированные ключом коллекции;
- `images`: ID, URL и alt изображений блоков.

У блока `data.fields` — объект полей, `data.items` — упорядоченный список однотипных элементов. Значение поля: `text`, `href`, `mediaId`, `published`. Скрытые поля возвращаются без содержимого; полностью скрытые элементы списка исключаются. Для изображения `text` задаёт alt блока; URL берётся из `images` по `mediaId`.

Общие блоки включаются в страницу автоматически: шапка, блоки страницы, форма, SEO, подвал. У политики нет формы заявки. Дополнительные поля формы аутстаффинга и продукта дополняют общую форму, а не создают ещё одну форму. `key` — фиксированный идентификатор места в шаблоне, а не редактируемый тег. Нельзя интерпретировать поля как HTML. Повторяющиеся декоративные метки могут оставаться текстом, но не управляют выбором сущностей.

У Product блоки `product-page-use-case-1`–`product-page-use-case-3` содержат собственные заголовки, описания, CTA и мобильные изображения сценариев. Одноимённые подборки в `collections` возвращают связанный кейс. Так сценарий сохраняет свой текст при переиспользовании кейса. Общая подборка `cases` также доступна. Список кейсов страницы `/cases` хранит собственный порядок и состав; полный каталог содержит также проекты главной и продукта.

Подборка с `allEntries=true` включает первые 100 опубликованных карточек. Для полного каталога используйте его API с пагинацией. У карточек специалистов и команды сразу доступны `specialist` и `member`; дополнительные запросы на каждую карточку не нужны.

Детальная страница возвращает `layout` с общими блоками и SEO конкретной записи, а также `content` — саму запись. Статья дополнительно возвращает `related`. Относительный `canonical` детальной страницы фронтенд разрешает относительно публичного домена. Шаблоны `service-detail`, `case-detail`, `specialist-detail`, `team-detail`, `blog-article` доступны редактору в списке страниц. Скрытый шаблон отключает соответствующий API детальной страницы.

У кейса галерея поддерживает загруженный `mediaId` либо исходный `sourceUrl`. При наличии обоих используйте загруженный файл. Исходные изображения доступных детальных кейсов сохранены ссылками на указанный сайт; они не загружались в MinIO. Их можно заменить файлами через админку. Если обложка не загружена, карточка кейса использует первое исходное изображение галереи.

У записей каталога можно отдельно выбрать `mobileCoverMediaId`; карточка возвращает `cover` и `mobileCover`. При отсутствии мобильного изображения используйте обычную обложку. Существующие мобильные изображения проектов переносятся в это поле.

## Административные API

Все маршруты `/api/admin/**` защищены HTTP Basic. Данные доступа задаются через окружение и не включаются в исходники.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `/api/admin/pages` | Фиксированные страницы |
| GET, PUT | `/api/admin/pages/{slug}` | Страница, SEO, схемы форм и подборки |
| PUT | `/api/admin/pages/{slug}/blocks/{id}` | Сохранить блок целиком |
| PUT | `/api/admin/pages/{slug}/collections/{id}` | Сохранить подборку |
| GET, POST | `/api/admin/catalog/{kind}` | Список / создание записи |
| GET, POST | `/api/admin/service-components/{kind}` | Список / создание элемента справочника услуги |
| GET, PUT, DELETE | `/api/admin/service-components/{kind}/{id}` | Просмотр, обновление, удаление неиспользуемого элемента |
| GET, PUT, DELETE | `/api/admin/catalog/{kind}/{id}` | Запись по ID |
| GET, POST | `/api/admin/catalog/{kind}/categories` | Категории / создание |
| GET, PUT, DELETE | `/api/admin/catalog/{kind}/categories/{id}` | Категория по ID |
| GET, POST | `/api/admin/blog/articles` | Статьи / создание |
| GET, PUT, DELETE | `/api/admin/blog/articles/{id}` | Статья по ID |
| GET, POST | `/api/admin/blog/categories` | Категории статей / создание |
| GET, PUT, DELETE | `/api/admin/blog/categories/{id}` | Категория статьи |
| GET, POST | `/api/admin/media` | Медиатека / multipart-загрузка |
| GET, PUT, DELETE | `/api/admin/media/{id}` | Файл / описание / удаление |
| GET | `/api/admin/leads` и `/api/admin/leads/{id}` | Заявки |
| PATCH | `/api/admin/leads/{id}` | Статус обработки заявки |

Для обновления обязательна текущая `version`: у каталога она находится в `entry.version`, у страницы — в `page.version`, у блока/подборки/категории — в `version`. При POST её можно не передавать. JPA optimistic locking защищает также одновременные запросы. ID и тип записи при обновлении не меняются.

Новая услуга сохраняется одним запросом:

```json
{
  "title": "Разработка Android-приложений",
  "slug": "android-development",
  "description": "Создаём приложения для бизнеса",
  "price": "от 400 000 ₽",
  "published": false,
  "sortOrder": 0,
  "coverMediaId": null,
  "categoryIds": [],
  "caseIds": [],
  "service": {
    "examplesTitle": "Примеры работ",
    "faqTitle": "Частые вопросы",
    "stackTitle": "Технологии",
    "stackDescription": "Нативная разработка",
    "processTitle": "Процесс работы",
    "tasksTitle": "Какие задачи решаем",
    "audienceTitle": "Кому подходит",
    "audienceDescription": "Для компаний и стартапов",
    "cooperationTitle": "Модели сотрудничества",
    "faq": [],
    "stack": [],
    "process": [],
    "tasks": [],
    "audience": [],
    "cooperation": []
  },
  "serviceSelections": {
    "faq": [],
    "stack": [],
    "process": [],
    "tasks": [],
    "audience": [],
    "cooperation": []
  }
}
```

При создании других видов записи передавайте соответственно `project`, `specialist` или `member`. Нужен ровно один вид содержимого. Списки внутри него обязательны, но могут быть пустыми. `categoryIds` всегда относится к выбранному каталогу. `caseIds` — упорядоченные ID кейсов и допустимы только у услуги; для остальных видов передавайте `[]`. Ссылка вычисляется из slug и префикса вида записи. Форматы полностью описаны в Swagger.

Для сохранения услуги `serviceSelections` обязателен; его шесть списков содержат выбранные ID в порядке отображения. Списки внутри `service` при POST/PUT должны быть пустыми: сохранение услуги не создаёт записи справочников. Для остальных каталогов `serviceSelections` не передаётся.

Типы административного справочника: `faq`, `stack`, `process`, `task`, `audience`, `cooperation`. Список поддерживает `page` и `size` как каталоги. Создание элемента процесса: `POST /api/admin/service-components/process` с `{"title":"Аналитика","description":"Изучаем задачу","price":null,"mediaId":null,"sortOrder":0}`. Для FAQ `title` — вопрос, `description` — обязательный ответ. У технологии допустимы название и `mediaId` логотипа, а описание и стоимость должны быть `null`. PUT требует текущую `version`. Идентичная запись возвращает 409 вместо создания дубликата.

Выбор существующего элемента: `"process":[{"componentId":12,"override":null}]` внутри `serviceSelections`. Индивидуальное описание: `{"componentId":12,"override":{"description":"Описание только для этой услуги"}}`. Отсутствующее поле или `null` наследует общее значение; пустая строка явно очищает поле, если для этого поля допустима пустота. ID должен относиться к соответствующему справочнику. Удаление используемого элемента возвращает 409; предварительно уберите его из услуг.

Публичный ответ услуги по-прежнему содержит развёрнутые `service.faq`, `stack`, `process`, `tasks`, `audience`, `cooperation` с учётом переопределений; `images` включает логотипы выбранных технологий. Дополнительно возвращается `serviceSelections` с ID связей. Потребителям публичного ответа не нужно запрашивать каждый элемент справочника отдельно.

Обновление блока: `{"version":0,"published":true,"data":{"fields":{...},"items":[...]}}`. Набор ключей каждого объекта должен совпадать со схемой из GET. Типы полей фиксированы: TEXT, LINK, IMAGE. В TEXT нельзя присвоить ссылку или изображение. Схема не принимается от клиента.

Обновление подборки:

```json
{
  "version": 0,
  "allEntries": false,
  "entryIds": [12, 15],
  "overrides": [{"entryId":12,"title":"Заголовок только на этой странице","description":null,"position":null,"imageAlt":null}]
}
```

Для всего каталога передавайте `allEntries=true`, `entryIds=[]`, `overrides=[]`. Переопределения относятся только к выбранным ID; `null` использует оригинальное значение. Привязка записи другого каталога запрещена.

Предел содержимого одной структурированной записи/блока/подборки — 1 МБ; списки каталогов до 100 элементов, списки фиксированного блока до 200. Уникальность адресов защищена БД. Удаление используемой категории, кейса или выбранной записи блокируется внешними ключами; сначала уберите связи либо скройте запись. Медиа, используемые в страницах, каталогах или статьях, удалить нельзя. Изображения не удаляются при удалении записи каталога.

Ошибки: 400 — неверные данные, 401 — авторизация, 404 — отсутствующая/скрытая запись, 409 — занятый адрес, конфликт версии или используемая связь, 413 — превышен размер загружаемого файла. Ответы ошибок — ProblemDetail.

## Перенос существующей базы

`StructuredContentMigration` выполняется после старых начальных загрузчиков при первом запуске новой версии. Новая схема создаётся существующим Hibernate `ddl-auto: update`. Перенос данных проходит в одной транзакции под PostgreSQL advisory lock. Успех фиксируется маркером `_system/structuredCmsV1`; при ошибке данные откатываются, при повторном запуске завершённый перенос не повторяется.

- Существующие услуги, проекты, специалисты, команда, тексты, ссылки, публикация и связи медиа переносятся в новые сущности. Если у карточки каталога были скрытые поля, запись переносится в черновик, чтобы не опубликовать скрытое содержимое. Все грейды специалиста, включая дополнительные, сохраняются списком.
- Общие процессы, задачи, аудитория и модели сотрудничества один раз копируются в каждую услугу как независимые начальные значения. Их последующее редактирование не меняет другие услуги.
- Затем `ServiceComponentsMigration` под тем же advisory lock переносит списки всех услуг в справочники, объединяя полностью одинаковые элементы по типу, текстам, стоимости и логотипу. Различающиеся элементы сохраняются отдельно; порядок и повторения сохраняются. В `service_offerings.body` остаются заголовки и пустые списки. Маркер `_system/serviceComponentsV1` предотвращает повторный перенос. Обновление уже развёрнутой структурированной базы тоже выполняет этот второй перенос; первая миграция повторно не запускается. При ошибке второй перенос откатывается целиком. База и файлы не очищаются.
- Начальные стеки Android, iOS, кроссплатформенной разработки и PWA переносятся отдельно; CRM, 1С и аутстаффинг получают наблюдавшиеся на сайте наборы технологий. Вкладки технологий главной сохраняют собственные описания. Подборка специалистов главной сохраняет свой состав и грейды, включая карточку, отсутствующую в каталоге страницы аутстаффинга.
- Старые `projectGroup`, `serviceGroup` и `filterN` преобразуются в связи только во время переноса; новый API их не использует.
- Различия карточек продукта и команды аутстаффинга переносятся в переопределения подборок.
- Начальные контакты, политика и доступное детальное содержимое кейсов взяты с `http://62.113.44.254:3003/` 18 октября 2026 года; снимки находятся в `src/main/resources/cms/`. Детальные страницы `skin-insights` и `vpn-app` были доступны; остальные известные ссылки кейсов не содержали детального контента. Их существующие карточки сохраняются, детали можно заполнить в админке.
- Статьи, заявки, OAuth-подключение amoCRM и файлы сохраняются в прежних таблицах/хранилище.
- `content_items` остаётся архивом. Старые ID медиа сохраняются в `archived_media_id` без внешнего ключа, чтобы архив не блокировал удаление уже неиспользуемого файла. Тексты и старые идентификаторы не удаляются.

`GET /api/admin/content` и `/api/content` читают архивный снимок, который больше не обновляется. POST/PUT/DELETE старого контента возвращают 410 Gone. Эти API не следует использовать для актуального сайта. Админка работает через новые маршруты.

Ответ `/api/pages/*` изменён несовместимо: вместо `sections/groupName/fields` используются фиксированные `blocks` и явные `collections`. Фронтенд необходимо подключить к новому контракту одновременно с переключением бэкенда. Исходников публичного фронтенда в этом репозитории нет; редактирование этого проекта не меняет автоматически сайт на порту 3003. Перед первым развёртыванием сохраните резервную копию существующей БД и томов; восстановление прежней версии приложения само по себе не отменяет миграцию данных.

## Окружение и запуск

Обязательные переменные: `POSTGRES_PASSWORD`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` (минимум 6 символов), `S3_SECRET_KEY`. Опциональные: `POSTGRES_DB`, `POSTGRES_USER`, `S3_ACCESS_KEY`, `CORS_ALLOWED_ORIGINS`.

`CORS_ALLOWED_ORIGINS` — список через запятую. По умолчанию разрешены `http://62.113.44.254:3003`, `http://localhost:3000`, `https://itwebs.ru`, `https://www.itwebs.ru`. Origin включает схему и порт. CORS настроен для `/api/**`; cookies не используются.

Для будущего развёртывания используется `docker compose --env-file .env up --build -d`. Команда выполняет сборку; в рамках текущей переработки она не запускалась. API и админка слушают порт 9999. PostgreSQL — 15432; MinIO API — 19000 и консоль — 19001 на loopback. Данные остаются в томах `postgres_data` и `minio_data`. Не удаляйте их при обновлении. Инструкция webhook-развёртывания — `deploy/README.md`.

Тесты, компиляция, сборка и запуск приложения в рамках этой переработки не выполнялись по запросу пользователя. Изменения проверялись чтением исходников и просмотром diff.

## amoCRM

Интеграция сохранена: новая заявка сначала сохраняется в PostgreSQL, затем передаётся в amoCRM со связанным контактом и примечанием. Ошибки отправки повторяются автоматически; состояние доступно в административном API заявок.

`POST /api/leads` дополнительно принимает необязательные `specialist` (до 120 символов), `grades` (до 20 строк по 120 символов) и `sourcePage` (до 1000 символов). Они сохраняются отдельными полями, возвращаются в административном API и включаются в примечание amoCRM. Форма аутстаффинга передаёт выбранного специалиста и грейды; остальные формы могут передавать только страницу отправки. Пример дополнительных полей: `{"specialist":"frontend","grades":["middle","senior"],"sourcePage":"/outstaff"}`.

Для OAuth задайте постоянный `AMOCRM_TOKEN_ENCRYPTION_KEY` (32 байта в base64, можно получить через `openssl rand -base64 32`). После подключения ключ нельзя менять без потери возможности расшифровать сохранённые токены. Обеспечьте HTTPS-доступность `/api/integrations/amocrm/secrets` и `/api/integrations/amocrm/callback`, затем откройте `/api/admin/integrations/amocrm/authorize` с административной авторизацией и разрешите подключение аккаунта. OAuth-реквизиты внешняя интеграция передаёт серверу; ручное задание client ID/secret не требуется.

Настройки: `AMOCRM_ACCOUNT_URL`, `AMOCRM_REDIRECT_URI`, `AMOCRM_PIPELINE_NAME`, `AMOCRM_STATUS_NAME`, опциональный `AMOCRM_RESPONSIBLE_USER_ID`, `AMOCRM_RETRY_DELAY_MS`. Заявки, полученные до OAuth-подключения, автоматически не переносятся.
